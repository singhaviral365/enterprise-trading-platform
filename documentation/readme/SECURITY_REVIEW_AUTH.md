## What changed since the previous review

| Area | Before (2026-09-25) | Now |
|---|---|---|
| Where the browser keeps the session | Both tokens in `localStorage` (`auth.session`) and sent as `Authorization: Bearer`, readable by any script on the page | Two **HttpOnly cookies** set by the auth service (`access_token`, path `/`, 15 min; `refresh_token`, path `/auth`, 7 days). `localStorage` keeps only the username and when the access cookie expires, nothing secret. A session saved by the old version is discarded and its tokens erased on first load. See [AUTH-COOKIES.md](AUTH-COOKIES.md) |
| API authentication | Bearer header only | Bearer header **or** the `access_token` cookie (auth service `JwtAuthGuard` / `JwtStrategy`, order-service `ApiAuthenticationFilter`). A malformed Authorization header is rejected, never papered over by the cookie |
| CSRF | Not applicable (no ambient credentials) | Needed now that a cookie authenticates. Cookies are `SameSite=Strict` by default, and a state-changing request authenticated by a cookie alone must carry `X-Requested-With` (enforced on `/auth/refresh`, `/auth/logout` and every non-safe method in `ApiAuthenticationFilter`) |
| Logout | None | `POST /auth/logout` revokes the presented refresh token and expires both cookies. The UI signs out at once and does not wait for it |
| Refresh in the browser | Not used by the UI | The interceptor renews the session before `expiresAt` or once after a 401, with no body (the cookie is the credential). Refreshes are single-flight in a tab and serialised across tabs with a Web Lock, because a refresh token works once. If the refresh is refused the session ends and the user is sent home |
| Login throttling | Not found | `LoginThrottleService`: 5 failures from one caller block that caller for 5 minutes. Weaknesses are recorded under A04 and A07 |
| CORS | Not explicitly enabled | Enabled with `credentials: true`, an allow-list of two hard-coded development origins, and `X-Requested-With` allowed |
| Replay (theft) detection | Not wired | **Still not wired** |
| Fallback JWT secret literals | Present | **Still present** |
| Container user | Root | **Still root** |
| `npm audit --omit=dev` (auth-service) | 15 (1 low, 8 moderate, 5 high, 1 critical) | **Same 15**, re-run on 2026-10-05 |

## Categories

| Category | In scope | Finding | Disposition |
|---|---|---|---|
| A01 Broken access control | Yes | `/auth/me` reads identity from verified JWT claims only (`src/auth/auth.controller.ts`, `src/auth/jwt-auth.guard.ts`). Registration always persists the `CUSTOMER` role (`AuthService.register`). The order-service filter takes the user id only from a JWT signed by the auth service; unsigned dev tokens exist but are off by default (`security.dev-tokens.enabled=false`, set to true only in the test configuration). Cookie authentication adds CSRF exposure, covered by `SameSite=Strict` plus the `X-Requested-With` requirement on non-safe methods and on refresh/logout, so a cross-site form cannot make a cookie-authenticated change. The Trade API checks that the account belongs to the token's user on every account route; a foreign account returns `ACC-409` (reads, place, cancel). The executor's `/api/v1/market` endpoints have no authentication at all (unchanged). | Mitigated. Residual risks: the CSRF header defence relies on the CORS allow-list staying tight; the market endpoints stay public (read-only market data); and a future route that trusts client-supplied account or role fields without a guard would reopen the gap. |
| A02 Cryptographic failures | Yes | Passwords hashed with Argon2id (`timeCost` 3, `memoryCost` 65536, `parallelism` 2) in `src/credentials/credentials.service.ts`. Access tokens are HS256 JWTs with signature, expiry and issuer checked. Refresh tokens are 32 random bytes, stored only as a SHA-256 hash. **Token storage changed:** tokens are now in HttpOnly cookies, so an XSS bug or compromised dependency can no longer read and exfiltrate them; they are no longer in `localStorage`. Cookie flags: `HttpOnly`, `SameSite=Strict`, refresh cookie scoped to `Path=/auth` so it never travels to the trading APIs. `Secure` defaults to on only when `NODE_ENV=production`; docker-compose defaults `AUTH_COOKIE_SECURE` to `false` for plain-http local runs. The JWT secret is shared with the order-service (symmetric HS256). Fallback secret literals remain in `src/app.module.ts` and `src/auth/jwt.strategy.ts`; `main.ts` calls `configuration()`, which throws if `JWT_SECRET` is missing, and `JwtAuthGuard` verifies against `process.env.JWT_SECRET \|\| ''`, which fails closed. The tokens are still returned in the JSON body for non-browser clients, and the browser ignores them. | Accepted. Residual risks: over plain http the cookies travel in clear text, so `AUTH_COOKIE_SECURE=true` and TLS are required anywhere beyond local development; anyone holding the shared HS256 secret can mint tokens; the fallback literals are reachable only in a bootstrap that skips `configuration()`; HttpOnly stops token theft but not an XSS bug acting as the user while the page is open. Follow-up: remove the fallback literals and reduce the body to `{ tokenType, expiresIn }` if no non-browser client needs the tokens. |
| A03 Injection | Yes | Data access uses TypeORM repository methods with bound values (`users.service.ts`, `refresh-tokens.service.ts`). The only raw SQL is static: the sequence reset in `database-init.service.ts` and the seed migration, neither of which takes untrusted input. The seed migration is not run (`migrationsRun: false`) and holds placeholder hashes that cannot verify. | Finding of none. Kept as is. Any future raw SQL must be parameterised and reviewed. |
| A04 Insecure design | Yes | Refresh tokens rotate: the presented token is revoked on successful refresh and a new pair is issued, and logout now revokes the token. **Replay detection is still not wired:** `AuthService.refresh` never calls `detectTheftAndRevoke`, and it could not tell a replay from an unknown token anyway, because `RefreshTokensRepository.findByHash` only returns rows with `revoked_at IS NULL`, so a consumed token looks the same as one that never existed. The comment on `refresh()` says the chain is revoked, which is not what the code does. **Login throttling now exists but is weak:** it is keyed by the first value of `X-Forwarded-For` (set by the client unless a trusted proxy overwrites it), so rotating that header gives every attempt a fresh counter; state is an in-memory map (per instance, lost on restart, entries only removed on success or after a block expires); it limits per caller, not per account; and a blocked caller still triggers a full Argon2 verification, so blocked traffic still costs CPU. Uniform login failure behaviour is implemented. The UI avoids causing false replays: single-flight refresh per tab and a Web Lock across tabs. Access tokens cannot be revoked, so after logout a stolen access token stays valid for up to 15 minutes. | Accepted. Residual risks: brute-force and credential stuffing are only partly slowed; a replayed refresh token is not contained or alerted; and once replay detection is wired it must distinguish "consumed" from "unknown" without punishing the legitimate multi-tab races the UI already guards against. Tracked in outstanding items. |
| A05 Security misconfiguration | Yes | **CORS is now enabled** (`src/main.ts`) with `credentials: true` and a hard-coded allow-list of two development origins; one entry (`http://127.0.0.1:5500/`) has a trailing slash and will never match a real `Origin`. Origins are not configurable per environment. Cookie `SameSite` and `Secure` are configurable (`AUTH_COOKIE_SAMESITE`, `AUTH_COOKIE_SECURE`; `none` forces `Secure`). Swagger UI and `/api-docs-json` are served unconditionally, with no authentication. No security-headers middleware (for example helmet) and no Content-Security-Policy on the Angular app. `GlobalExceptionFilter` still logs the full Error object for unhandled faults. The Dockerfile still has no `USER` directive, so the container runs as root. | Accepted. Residual risks: root execution increases blast radius on a container escape; verbose error logging can expose internals in shared logs; public API docs and missing CSP/headers widen the surface; hard-coded CORS origins will break or be over-widened at deployment. Hardening is carried to the outstanding items. |
| A06 Vulnerable and outdated components | Yes | Re-ran `npm audit --omit=dev` in `services/auth-service` on 2026-10-05: 15 vulnerabilities (1 low, 8 moderate, 5 high, 1 critical), unchanged since 2026-09-25, through NestJS transitive dependencies, multer/body-parser, `uuid`, and `tar` via `@mapbox/node-pre-gyp`. `package-lock.json` is present and pinned. The Angular app is clean: `npm audit --omit=dev` in `frontend` reports 0 vulnerabilities. | Accepted. A forced fix needs breaking upgrades (Nest major and related stack), which was not run at sprint close. Residual risk: known vulnerable transitive packages remain in the auth-service runtime until the planned upgrade and regression cycle. |
| A07 Identification and authentication failures | Yes | Unknown user and wrong password both return `AUTH-401` and run Argon2 against a dummy hash to keep timing comparable. Access token expiry, issuer, signature and claim shape are enforced on every protected request. Register does not issue tokens. Password rules are enforced in the DTO and mirrored in the UI. **Session lifecycle in the browser:** sign-out revokes the refresh token server-side and clears the cookies; an expired access cookie is renewed by the interceptor; when the refresh token is refused the UI clears its session, shows a notice and redirects to the home page; a restored session whose access cookie has expired is renewed on its first request instead of being trusted. Registration returns `AUTH-409` for a taken username or email, which lets a caller test whether a name exists (this follows the contract). No account lockout and no second factor. | Mitigated. Core authentication controls are in place. Residual risks: login throttling is bypassable (see A04); there is no per-account lockout, so a distributed attack is not slowed; and username/email existence can be probed through registration. |
| A09 Security logging and monitoring failures | Yes | `RedactingLogger` redacts sensitive keys (password, token, authorization, jwt and similar) before logging, and the order-service logs a warning for a cookie-authenticated change without the CSRF header. Login failures, refresh and logout emit events. There is no replay-specific event because replay detection is not wired, and throttle blocks are not logged as such (a blocked attempt is logged like any failed login). | Mitigated. Redaction reduces token leakage. Residual risk: weaker visibility of replay attempts and of throttle blocking until those events exist. |
